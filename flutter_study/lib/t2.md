## 一、三棵树与复用机制

### 1. Flutter 三棵树是什么？
**答：`Widget` 负责描述，`Element` 负责连接和复用，`RenderObject` 负责布局和绘制。**  
`Widget` 是不可变配置；`Element` 是运行时实例；`RenderObject` 才是真正干渲染的对象。

### 2. 为什么 Flutter 要有三棵树？
**答：为了把“声明式配置”“生命周期管理”“渲染执行”拆开。**  
这样 Widget 可以频繁重建，而更贵的 Element、State、RenderObject 尽量复用。

### 3. `BuildContext` 本质是什么？
**答：`BuildContext` 本质上就是 `Element` 对外暴露的接口。**  
对框架来说它是 Element，对业务代码来说它是更安全的上下文能力入口。

### 4. Flutter 复用的核心是什么？
**答：Flutter 不是复用 Widget，而是复用 `Element`、`State`、`RenderObject`。**  
Widget 本来就很轻，真正贵的是运行时实例和渲染对象。

### 5. `updateChild` 的作用是什么？
**答：它负责决定旧 child 能不能复用，以及是否需要创建新 Element。**  
这是 Flutter 子节点更新的核心入口。

### 6. `updateChild(child, newWidget, newSlot)` 里 `child` 和 `newWidget` 分别是谁？
**答：`child` 是旧的子 Element，`newWidget` 是这次 build 产出的新子 Widget。**  
框架是在问：“这个旧 Element 能不能继续服务这次的新配置？”

### 7. 为什么是“旧 Element + 新 Widget”对比，而不是“旧 Element + 新 Element”？
**答：因为新 Element 这时还没必要创建，先判断能不能复用更省。**  
如果每次都先 new 一个新 Element 再比较，会浪费对象创建和生命周期成本。

### 8. 判断 Element 能不能复用的标准是什么？
**答：看新旧 Widget 的 `runtimeType` 和 `key`。**  
两者一致，通常就能走 `Widget.canUpdate`，复用旧 Element。

### 9. `key` 和 `slot` 分别管什么？
**答：`key` 管身份，`slot` 管位置。**  
`key` 决定“是不是同一个 child”，`slot` 决定“这个 child 现在挂在哪儿”。

### 10. `slot` 是什么？
**答：`slot` 是父 Element 给子 Element 的位置标记。**  
单子节点通常是 `null`，多子节点通常是 `IndexedSlot(index, previousSibling)`。

### 11. 为什么 child 复用了，还要更新 `slot`？
**答：因为“还是原来那个 child”不代表“还在原来的位置”。**  
复用的是对象身份，更新的是它在父节点里的挂载位置和对应 RenderObject 的顺序。

### 12. `slot` 最典型用在什么场景？
**答：多子节点重排。**  
比如 `Row(children: [A, B, C])` 变成 `Row(children: [A, C, B])`，child 本身可复用，但位置变了。

### 13. 如果 Element 顺序和 RenderObject 顺序不同步，会怎样？
**答：代码逻辑和实际显示、点击、遮挡都会错。**  
你以为顺序已经变了，但渲染树还是按旧顺序画和命中。

### 14. `Stack(children: [A, B]) -> Stack(children: [B, A])` 为什么可能遮挡出错？
**答：因为 Stack 里后画的 child 在上层。**  
如果 RenderObject 顺序没同步，界面上仍然可能是 `B` 盖住 `A`。

## 二、State 生命周期与 build

### 15. `StatefulWidget` 首次挂载的调用顺序是什么？
**答：`initState -> didChangeDependencies -> build`。**  
首次不是复用，而是全新创建 State。

### 16. `StatefulWidget` 被复用时，常见调用顺序是什么？
**答：最常见是 `didUpdateWidget -> build`。**  
如果依赖的 InheritedWidget 也变了，则可能是 `didUpdateWidget -> didChangeDependencies -> build`。

### 17. `didUpdateWidget` 什么时候触发？
**答：父组件传入的新 Widget 和旧 Widget 可复用时触发。**  
也就是 State 被保住了，但 `widget.xxx` 配置变了。

### 18. `didChangeDependencies` 什么时候触发？
**答：当依赖的 `InheritedWidget` 变化时触发。**  
比如 `Theme`、`MediaQuery`、`Localizations`、`Provider` 变化。

### 19. 逻辑该写在 `didUpdateWidget` 还是 `didChangeDependencies`？
**答：参数变化写 `didUpdateWidget`，上下文依赖变化写 `didChangeDependencies`。**  
前者看 `widget.xxx`，后者看 `Theme.of(context)` 这类 inherited 数据。

### 20. 可以在 `didUpdateWidget` 里调用 `setState` 吗？
**答：可以，但通常是冗余的。**  
因为框架在 `didUpdateWidget` 后本来就会继续 `build`。

### 21. 可以在 `didChangeDependencies` 里调用 `setState` 吗？
**答：可以，但通常也没必要。**  
因为依赖变化后框架本来就会继续 `build`，额外 `setState` 往往只是增加噪音。

### 22. `setState` 为什么不是立刻刷新？
**答：它的职责不是立刻重绘，而是标记 dirty，下一帧统一更新。**  
这样可以合并多次状态变化，对齐屏幕刷新节奏，保证渲染流程稳定。

## 三、RenderObject 复用与渲染

### 23. RenderObject 是怎么复用的？
**答：RenderObject 的复用建立在 RenderObjectElement 复用成功的前提上。**  
首次挂载走 `createRenderObject`，后续复用走 `updateRenderObject`。

### 24. RenderObject 为什么说是“跟着 Element 一起复用”的？
**答：因为它不单独做新旧对比，它的生死绑定在所属的 RenderObjectElement 上。**  
Element 复用成功，旧 RenderObject 才继续活着。

### 25. `updateRenderObject` 真正在做什么？
**答：把新 Widget 配置同步到旧 RenderObject。**  
它不是重建渲染对象，而是更新旧对象的属性。

### 26. `updateRenderObject` 后为什么还会继续渲染？
**答：因为 RenderObject 的属性 setter 会按需调用 `markNeedsLayout`、`markNeedsPaint` 等脏标记。**  
真正决定是否重新布局、重绘、更新图层的是 RenderObject 自己。

### 27. 什么叫重新布局？
**答：重新计算“多大、放哪儿”。**  
也就是重新算尺寸、约束和子节点位置。

### 28. 什么叫重绘？
**答：重新计算“长什么样、怎么画”。**  
也就是重新输出颜色、文字、背景、边框、图片等视觉结果。

### 29. 重新布局和重绘的区别是什么？
**答：布局管几何，绘制管外观。**  
布局变化往往会带来后续重绘；但重绘不一定触发布局。

### 30. 哪种变化通常只会重绘，不会重新布局？
**答：颜色、阴影、边框颜色、透明度这类外观变化。**  
因为尺寸和位置没变，只是画法变了。

### 31. 哪种变化通常会触发布局？
**答：宽高、padding、文本长度、对齐方式、flex 等几何相关变化。**  
因为它们会影响尺寸或位置。

### 32. 什么是图层合成更新？
**答：当透明度、变换、滤镜等合成层属性变时，可能更新图层而不一定重新布局。**  
这比完整 layout 便宜，但也不是零成本。

## 四、事件、RunLoop、启动

### 33. iOS 手指触摸屏幕后，大致流程是什么？
**答：硬件采样 -> RunLoop 收事件 -> UIApplication 分发 -> UIWindow 命中测试 -> 响应链/手势识别 -> 如有需要再刷新界面。**  
RunLoop 是事件驱动和界面刷新的核心调度器。

### 34. 前台静止页面、没有手势时，主线程 RunLoop 在做什么？
**答：大多数时间是在等待/休眠。**  
不是一直 60Hz 重跑界面，而是等下一个事件把它唤醒。

### 35. Flutter 手指触摸屏幕后，大致流程是什么？
**答：原生系统收事件 -> Flutter Engine 转成 Pointer 事件 -> Framework 做命中测试和手势竞技 -> 业务回调 -> 如有状态变化再走渲染流水线。**  
输入先经过宿主平台，UI 更新再走 Flutter 自己的树。

### 36. App 冷启动全过程是什么？
**答：系统创建进程 -> 加载可执行文件和动态库 -> Runtime 初始化 -> 进入应用生命周期 -> 业务初始化 -> 首屏构建 -> 首帧渲染。**  
本质上就是从“没有进程”到“首帧可见”。

### 37. Flutter App 冷启动比原生多了什么？
**答：还多了 FlutterEngine、Dart VM/Isolate、Dart `main()`、`runApp()` 和三棵树构建。**  
这也是 Flutter 冷启动分析里常见的额外链路。

## 五、图片缓存与性能优化

### 38. `memCacheWidth / memCacheHeight` 是做什么的？
**答：控制“这次解码进内存”的位图尺寸。**  
它主要是为了降低 Flutter `ImageCache` 的内存占用。

### 39. `maxWidthDiskCache / maxHeightDiskCache` 是做什么的？
**答：控制“写入磁盘缓存”的缩略图上限尺寸。**  
它针对的是本地缓存文件，不是当前这次内存解码大小。

### 40. 只传 `memCacheWidth` 不传 `memCacheHeight` 会怎样？
**答：会按给定宽度解码，高度按原图比例等比缩放。**  
单传一边通常最稳，不容易失真。

### 41. 同时传 `memCacheWidth` 和 `memCacheHeight` 会怎样？
**答：如果比例和原图差异大，可能变形。**  
所以双传两边时，要自己保证目标比例合理。

### 42. 为什么磁盘参数叫 `max`，内存参数不叫 `max`？
**答：磁盘层是在生成“上限缩略图文件”，内存层是在指定“目标解码尺寸”。**  
两层解决的不是同一个问题。

### 43. `allowUpscaling` 是什么意思？
**答：是否允许按超过原图尺寸的目标大小去解码。**  
默认是 `false`，因为放大解码不会增加细节，只会增加成本。

### 44. `useOldImageOnUrlChange` 是做什么的？
**答：同一个图片组件运行中切换 `imageUrl` 时，新图没准备好前要不要继续显示旧图。**  
它本质上对应 Flutter `Image.gaplessPlayback`。

### 45. `useOldImageOnUrlChange` 会在 App 重启时先生效显示本地缓存图吗？
**答：不会。**  
它不是给“冷启动读磁盘缓存”用的，而是给“同一个 State 里切换 URL”用的。

### 46. `cached_network_image` 的磁盘缓存需要手动清理吗？
**答：一般不用，因为默认就有过期和容量淘汰机制。**  
默认大致是 30 天和 200 个对象，但图片变体多时建议自定义 CacheManager。

### 47. 同一个 URL，不同 `maxWidthDiskCache` 会不会生成多个本地文件？
**答：会。**  
磁盘缩略图 key 会把尺寸拼进去，所以不同尺寸会生成不同变体。

### 48. 同一个 URL，不同 `memCacheWidth` 会不会生成多个内存位图？
**答：也会。**  
因为 Flutter 内存缓存 key 里会把解码尺寸也纳入区分。

### 49. 这会不会导致缓存反而变大？
**答：会，所以同一类场景最好统一几个固定尺寸档位。**  
尺寸策略太散，命中率会下降，内存和磁盘都容易膨胀。

### 50. 页面上 5 个相同 URL 的图片组件，会发 5 次网络请求吗？
**答：同 key、同尺寸配置时，通常不会。**  
Flutter `ImageCache`、`flutter_cache_manager` 都有同 key 合并加载机制。

### 51. 那什么情况下同 URL 也可能出现多份加载变体？
**答：当 `cacheKey`、磁盘尺寸、内存尺寸不同的时候。**  
这时系统会把它们视为不同资源变体来缓存和解码。

### 52. 列表缩略图怎么配？
**答：按实际显示尺寸乘设备像素比来配 `memCache`，磁盘尺寸和内存接近或略大。**  
目标是省内存、省解码时间、滚动流畅。

### 53. 详情图怎么配？
**答：磁盘尺寸别压太小，内存解码按详情页实际显示尺寸来。**  
目标是保证画质，同时避免超大原图直接进内存。

### 54. 瀑布流怎么配？
**答：优先按卡片实际宽度控制 `memCacheWidth`，磁盘尺寸略大一档。**  
目标是平衡滚动性能和视觉质量。

## 六、高频一句话题

### 55. 用 50 字讲 Flutter 三棵树
**答：Widget 树描述配置，Element 树管理实例与复用，RenderObject 树负责布局绘制命中测试；三者协作实现声明式更新与高性能渲染。**

### 56. 用 50 字讲 Flutter 渲染机制
**答：状态变化先触发构建配置树，再复用元素树并更新渲染对象，随后完成布局、绘制与图层合成，最终呈现在屏幕上。**

### 57. 一句话讲 `slot`
**答：`slot` 是父 Element 给子 Element 的位置说明书，单 child 常为 `null`，多 child 常用于重排与移动 RenderObject。**

### 58. 一句话讲 `didUpdateWidget` 和 `didChangeDependencies`
**答：前者响应外部传参变化，后者响应 Inherited 依赖变化。**

### 59. 一句话讲 `setState`
**答：`setState` 不是立刻重绘，而是标记当前节点 dirty，下一帧统一 build、布局和绘制。**

### 60. 一句话讲 RenderObject 复用
**答：首次挂载创建 RenderObject，后续复用只更新旧对象属性，再由它自己决定要不要 layout、paint 或更新图层。**

## 七、收尾模板

### 61. 如果面试官让你把 Flutter 更新链路串起来，怎么答？
**答：先 `setState` 标记脏节点，下一帧重新 `build` 产出新 Widget，再由 `updateChild` 判定 Element 是否复用；如果复用成功，State 和 RenderObject 也尽量保留，最后由 RenderObject 按需触发布局、绘制和图层更新。**

### 62. 如果面试官让你把图片性能优化讲成一句话，怎么答？
**答：图片优化的核心是控制磁盘变体数量、控制内存解码尺寸、统一场景尺寸档位，避免同 URL 产生过多缩略图和位图缓存变体。**

## 八、通用架构题

### 63. 如何理解 Flutter 渲染机制？
**答：状态变化后先重新 build 产出新 Widget，再复用 Element 并更新 RenderObject，最后进入布局、绘制和图层合成。**  
Flutter 不是频繁操作原生控件树，而是维护自己的渲染树和流水线。

### 64. 如何理解 Flutter 内存管理？
**答：底层靠 Dart GC 回收无引用对象，业务层靠开发者管理对象生命周期。**  
像 `Controller`、订阅、监听器、图片缓存这类对象，如果一直被引用，就不会被自动“神奇释放”。

### 65. 如何理解 Flutter 异步？
**答：`async/await` 本质是事件循环调度，不等于开新线程。**  
IO 用 `Future` 很合适，但 CPU 密集任务要放到 `Isolate`，否则容易卡主 UI。

### 66. 如何理解 Flutter 内存优化？
**答：核心是控制图片、缩短大对象生命周期、避免无意义常驻引用。**  
图片通常是大头，所以按显示尺寸解码、统一尺寸档位特别重要。

### 67. 如何理解 Flutter 性能优化？
**答：核心是减少每一帧 16ms 内主线程要做的工作量。**  
常见抓手是减少无效 build、减少无效重绘、避免主线程做重计算。

## 九、图片体系题

### 68. 什么是 `ImageProvider`？
**答：`ImageProvider` 是 Flutter 图片系统里的数据源抽象。**  
它负责描述图片从哪来、怎么生成缓存 key、以及怎么把图片加载成可消费的图片流。

### 69. iOS 有没有类似 `ImageProvider` 的概念？
**答：UIKit 没有完全一一对应的单一对象。**  
类似职责通常分散在 `UIImage` 加载、缓存层和 `UIImageView` 显示层里，像 `SDWebImage` 这种第三方库更接近它的思路。

### 70. 为什么很多项目用 `cached_network_image` 而不是 `Image.network`？
**答：因为前者在原生网络图显示之外，还补了磁盘缓存、占位图、进度、错误态和缓存策略控制。**  
`Image.network` 适合简单显示，`cached_network_image` 更适合真实业务里的列表流和高频图片场景。

### 71. `Image.network` 和 `cached_network_image` 的相同点是什么？
**答：两者最终都走 Flutter 图片管线，也都能用内存缓存。**  
它们都会经过 `ImageProvider -> ImageStream -> 解码 -> 绘制` 这条链。

### 72. `Image.network` 和 `cached_network_image` 的最大区别是什么？
**答：最大区别是后者多了磁盘缓存和完整的图片体验封装。**  
也就是 App 重启后还能更容易直接复用本地文件，而且占位、进度、错误处理都更顺手。

### 73. `UIImage(named:)` 和 `UIImage(contentsOfFile:)` 有什么区别？
**答：`named:` 更适合包内频繁复用的小图，`contentsOfFile:` 更适合大图或临时文件。**  
前者带系统缓存语义，后者更像按路径直接加载。

### 74. `UIImage(named:)` 和 `UIImage(contentsOfFile:)` 都会带内存缓存吗？
**答：`named:` 有明显缓存语义，`contentsOfFile:` 没有这层便捷缓存语义。**  
如果你希望后者也缓存，通常要自己配 `NSCache` 或图片库。

### 75. `UIImage(named:)` 和 `UIImage(contentsOfFile:)` 都会自动解码吗？
**答：它们最终都会进入系统解码链路，但不代表创建对象那一刻就完成最终位图解码。**  
很多解码成本会在第一次真正显示到屏幕时暴露出来。

### 76. 为什么图片第一次显示会卡？
**答：因为压缩图片第一次上屏前要解码成位图，解码、缩放和像素拷贝都可能很耗时。**  
如果这一步刚好落在首屏、滑动或列表复用的关键路径上，就容易掉帧。

### 77. 图片首次显示卡顿，怎么一句话讲优化方向？
**答：核心是预加载、按显示尺寸解码、列表用缩略图、避免超大图直接上屏。**  
本质上就是把解码成本前移、降级，别让它在关键帧里集中爆发。

## 十、背诵建议

1. 第一轮只背每题第一句加粗答案。
2. 第二轮把“为什么”补成第二句。
3. 源码题优先背：`updateChild`、`didUpdateWidget`、`RenderObject` 复用、`slot`、图片缓存尺寸。
4. 系统题优先背：iOS 触摸、Flutter 触摸、冷启动、`setState` 为什么下一帧刷新。
5. 图片题优先背：`ImageProvider`、`Image.network vs cached_network_image`、`memCache`、`maxDiskCache`、`allowUpscaling`、`useOldImageOnUrlChange`、同 URL 多组件请求合并。
